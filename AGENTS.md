# Triosteum — правила для агентов (Codex и Claude)

В проекте работают два ИИ-агента: **Codex** (ChatGPT) и **Claude**. Каждый работает в своей среде,
вносит изменения через запросы на слияние (PR) и проверяет PR другого. Владелец репозитория — LesNyXiX.

## Язык
- Описания PR, ревью, комментарии к коду, сообщения коммитов и тексты интерфейса — **на русском**.

## Как устроен проект
- Исходники: `src/` (модули перечислены по порядку в `src/manifest.json`, собираются в одну область видимости).
- Сборка: `node build.mjs` → `docs/index.html` (сайт на GitHub Pages из `/docs`). Сборку **коммитить** вместе с исходниками.
  `TRIOSTEUM_DEV=1 node build.mjs` — без минификации, только для отладки, такую сборку не коммитить.
- Сервер: `server/` (FastAPI), тесты — `cd server && pytest`.
- Тесты интерфейса: Playwright, `npm test` и `npm run test:<набор>` (список — в `package.json`, весь набор — в `.github/workflows/tests.yml`).
  Новая функция — с тестом. Перед PR прогнать хотя бы затронутые наборы.

## Порядок работы
1. Одна задача — одна ветка: `codex/<кратко>` или `claude/<кратко>`. В `main` напрямую не пушить.
2. Перед началом — свежий `main`. Не браться за то, над чем уже есть открытый PR другого агента: проверить список открытых PR.
3. PR: что сделано и зачем, как проверено (какие тесты), что осталось. Маленькие PR лучше больших.
4. Ревью: каждый PR проверяет **другой** агент. Claude прогоняет все тесты и смотрит результат в браузере.
5. Слияние: когда проверки GitHub Actions зелёные и в ревью нет замечаний уровня P0/P1. Сливает Claude (squash) или владелец.
6. Не больше **двух кругов** исправлений по замечаниям на один PR — дальше решает владелец (комментарий с вопросом к нему).
7. Конфликт с чужим PR — не перезаписывать чужую работу: влить `main`, объединить лучшее из обоих, написать в PR, что взято.

## Обязательные ограничения
- Ничего, что требует оплаты (платные сервисы, API, подписки), — не подключать; такие идеи — отдельным issue «отложено: платно».
- Ключи API и пароли — секреты: не коммитить, не печатать в логах, не класть в localStorage вне предусмотренных мест.
- Не отправлять почту владельца и другие личные данные во внешние сервисы.
- Не использовать товарные знаки Photoshop / Illustrator как названия функций или продуктов.
- В JS-коде, который попадает в `<script>`, не должно быть буквальной последовательности `</script` (сборка упадёт) — экранировать как `<\/script>`.
- Не ломать работу без сервера: сайт на GitHub Pages открывается как статический файл.

## Review guidelines
- Отмечать только реальные проблемы: P0 — поломка/потеря данных/уязвимость, P1 — заметная ошибка поведения или регрессия.
- Проверить: собран ли `docs/index.html` из этих исходников; есть ли тест на новое поведение; не задеты ли
  сохранение данных (localStorage/IndexedDB), работа на телефоне (касания), тёмная и светлая темы, доступность (клавиатура, aria).
- Производительность: не читать размеры элементов в циклах между записями стилей, не вешать `backdrop-filter` на большие слои,
  на доске с сотнями блоков — без перерисовки всего на каждый кадр.
- Названия CSS-классов — уникальные: уже были столкновения (`.opt`, `.mini`).
